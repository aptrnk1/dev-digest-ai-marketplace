# Spec: Marketplace Catalog Site — статичний пошуковий каталог плагінів Dev Digest AI
Spec ID: SPEC-2026-10-25-marketplace-catalog-site
Status: draft
Supersedes: —
Modules: site, index-build, ci
Design: `docs/features/marketplace-site/design/Catalog.dc.html` (+ `support.js`) — інтерактивний макет усіх екранів

## Проблема й користувач
Користувач Claude Code, який прийшов у маркетплейс `dev-digest` (репо
`aptrnk1/dev-digest-ai-marketplace`), хоче знайти потрібний артефакт: плагін,
skill, agent, command, hook або MCP-сервер. Формулює він це природною мовою,
наприклад «мені треба скіл для code review» або «I need a skill for code review». Зараз є лише таблиця плагінів у
`README.md` і сирі файли (`.claude-plugin/marketplace.json`,
`plugins/<name>/.claude-plugin/plugin.json`, `plugins/<name>/skills/*/SKILL.md`).
Пошуку по вмісту немає. Перед встановленням не видно, які hooks чи MCP-сервери
плагін запустить з правами користувача, хоча `README.md` прямо просить їх
переглянути. Ще команді незручно рознести набір плагінів по репозиторію, а
стежити за новими версіями нема де.

Репо — Claude Code plugin marketplace без бекенду. Зараз у ньому 5 плагінів
(`hello`, `engineering-paved-path`, `research-tools`, `architecture-review`,
`sdd-engineering`: 10 skills, 6 agents, 1 `hooks.json`) і CI `validate.yml`, який на PR і push у `main`
запускає лише `claude plugin validate . --strict` та валідацію кожного плагіна.

## Goals / Non-goals
**Goals**
- **MVP.** Статичний сайт на GitHub Pages, без бекенду. Мова UI — українська.
  Технічні терміни (`skill`, `hook`, `MCP`, `Copy install`) і команди Claude
  Code лишаються як у макеті. Повідомлення CI та вміст бейджів shields.io
  (AC65, AC70) лишаються англійською: їх читають у логах і README, а не на
  сайті. Звичайний HTML/CSS/JS без фреймворку і без SSG; дозволено легку
  клієнтську бібліотеку пошуку.
- **MVP.** Індекс збирається в GitHub Actions на push у `main` і на
  `workflow_dispatch`. Він містить шість типів артефактів: plugin, skill,
  agent, command, hook, mcp. Дані беруться з `marketplace.json`, `plugin.json`,
  frontmatter і тіла `SKILL.md`, `agents/*.md`, `commands/*.md`, з
  `hooks/hooks.json`, `.mcp.json` та з компонентів, які задав `plugin.json`.
- **MVP.** Пошук ключовими словами в браузері: стоп-слова й слова-типи
  українською та англійською, буст полів, prefix і fuzzy, карта синонімів
  (зокрема українсько-англійська), теги.
- **MVP.** Картки результатів: тип, назва, підсвічений сніпет, батьківський
  плагін, копіювання команди встановлення, команда виклику, бейджі ризику.
- **MVP.** Головна: hero-пошук, чипи популярних тегів, лічильники за типами,
  блок «Переглянути за типом».
- **MVP.** Сторінка плагіна: відрендерений і санітизований README, склад
  плагіна, версія, команда встановлення, блок «Що цей плагін запускає на
  вашій машині».
- **MVP.** Сторінка артефакту (skill, agent, command, hook, mcp): хлібні
  крихти, команда виклику, `Tools / permissions` з frontmatter, документація
  (санітизоване тіло Markdown).
- **MVP.** Сторінка «Як підключити marketplace»: три кроки з командами.
- **MVP.** Палітра команд `⌘K` / `Ctrl+K` для швидкого переходу до артефакту.
- **MVP.** Фільтри за типом, категорією, тегами й автором; сортування за
  релевантністю або назвою; стан пошуку живе в URL.
- **MVP.** Ручний перемикач світлої й темної теми. За замовчуванням — системна
  тема, вибір запам'ятовується в браузері.
- **MVP.** Кнопка «Запропонувати плагін», що відкриває GitHub Issue з
  підставленими полями.
- **MVP.** Фікстурний маркетплейс для тестів поза
  `.claude-plugin/marketplace.json`. Продакшн-індекс містить лише реальні
  плагіни.
- **v2.** Team bundle builder: генерує сніпет `.claude/settings.json` з
  `extraKnownMarketplaces` + `enabledPlugins`.
- **v2.** Що нового: історія версій кожного плагіна з git, обчислена в CI,
  плюс Atom-фід, блок «Що нового» на головній, дата «оновлено» і сортування
  «Нещодавно оновлені».
- **v2.** Бейджі для README: статичні endpoint-JSON для shields.io.

**Non-goals**
- Семантичний пошук і embedding-и (можливо, пізніше).
- Генератор плагінів; валідатор у браузері.
- Рейтинги й відгуки (giscus); лічильники встановлень і переглядів.
- Будь-які runtime-виклики GitHub API з браузера. Усе, що потребує GitHub,
  обчислюється в CI (R4).
- Оновлення індексу без rebuild: сайт показує стан на момент останнього build.
- Додавання справжніх демо-плагінів у маркетплейс (тестові дані — лише фікстури).
- Вибір accent-кольору (у макеті це параметр прев'ю, а не функція для
  користувача). Accent фіксовано синій.
- Поле `compatibility` з макета (напр. `Claude Code ≥ 1.4`): маніфест плагіна
  не має поля для мінімальної версії Claude Code (R8), тож даних для нього
  немає.
- Інше поза цією спекою (кандидати на наступні ітерації, без AC): оцінка
  вартості контексту в токенах, бейдж evals і сигнали якості, «Схожі
  артефакти», workflows/рецепти, публічний `llms.txt` і мета-skill
  `find-plugin`, завантаження skill як `.zip`, «Мій стек», стартові набори за
  ролями, порівняння плагінів.

## User stories
- **US1** Як користувач Claude Code, я вводжу запит природною мовою, щоб
  побачити всі артефакти маркетплейсу, які йому відповідають.
- **US2** Як користувач, я звужую результати за типом, категорією й тегами і
  ділюся посиланням на цей пошук, щоб колега побачив ті самі результати.
- **US3** Як користувач, я копіюю команду встановлення плагіна або виклику
  skill/command, щоб одразу виконати її в Claude Code.
- **US4** Як користувач, я відкриваю сторінку плагіна, щоб прочитати README,
  побачити версію і всі його компоненти.
- **US12** Як користувач, я відкриваю сторінку окремого skill чи agent, щоб
  прочитати його документацію і побачити, які інструменти він може
  використовувати.
- **US13** Як новий користувач, я відкриваю «Як підключити marketplace», щоб
  за три кроки додати маркетплейс, поставити плагін і знати, як його
  оновлювати.
- **US14** Як користувач, що знає назву, я натискаю `⌘K`, щоб перейти до
  артефакту, не відкриваючи сторінки пошуку.
- **US15** Як користувач, я перемикаю світлу й темну тему, щоб читати
  каталог так, як мені зручно.
- **US5** Як обережний користувач, я бачу, які hooks, MCP-, LSP-сервери,
  monitors і бінарники запустить плагін, щоб вирішити, чи довіряю йому, ще до
  встановлення.
- **US6** Як користувач, який не знайшов потрібного, я пропоную новий плагін
  через GitHub Issue, щоб мейнтейнер про це дізнався.
- **US7** Як мейнтейнер маркетплейсу, я мерджу зміни в `main`, і сайт з
  індексом оновлюється автоматично. Зламаний плагін зупиняє деплой, щоб на
  сайт не потрапили биті дані.
- **US8** Як мейнтейнер, я веду карту синонімів і теги, щоб запити
  користувачів знаходили артефакти, навіть коли слова в запиті й у
  документації різні.
- **US9** (v2) Як тімлід, я вибираю кілька плагінів і отримую готовий
  `.claude/settings.json`, щоб уся команда отримала маркетплейс і плагіни
  через репозиторій.
- **US10** (v2) Як користувач, я бачу історію версій плагінів і підписуюся на
  Atom-фід, щоб знати про нові релізи.
- **US11** (v2) Як автор плагіна, я копіюю Markdown бейджа з версією, щоб
  вставити його в README.

## Дизайн
Макет: `docs/features/marketplace-site/design/Catalog.dc.html` (відкривається
в браузері разом із `support.js`). Він інтерактивний: усі екрани в одному
файлі, перемикаються кліками. Дані в макеті вигадані (плагіни `react-tools`,
`mcp-postgres` тощо). Сайт показує лише реальні дані з індексу. Макет задає
розкладку, токени кольорів (`--bg`, `--text`, `--accent`, `--kind-*` для
світлої та темної тем), шрифти IBM Plex Sans / Mono і тексти UI. Точні рядки
UI процитовано в AC. Де AC і макет розходяться, діє AC.

| D# | Екран у макеті (`screen`) | Екран сайту |
|----|---------------------------|-------------|
| D1 | `home` (+ `catalogEmpty`) | Головна `/` без параметрів; порожній каталог |
| D2 | `search` | Результати `/?q=…` або з фільтрами |
| D3 | `plugin` | Сторінка плагіна `/plugin.html` |
| D4 | `artifact` | Сторінка артефакту `/artifact.html` |
| D5 | `getting-started` | `/getting-started.html` |
| D6 | `whats-new` | `/whats-new.html` (v2) |
| D7 | палітра `⌘K`, toast «Скопійовано» | Оверлеї на всіх сторінках |

**Відхилення від макета (свідомі):**
- У хедері макета немає навігації. На сайті є посилання `Як підключити`, а у
  v2 ще `Що нового` і `Набір для команди`.
- Макет показує `compatibility`. На сайті його немає (див. Non-goals).
  `Залежності` беруться з `dependencies` у `plugin.json` (AC88, AC89).
- Макет показує виклик агента як `@<name>`. На сайті це повний виклик
  `@agent-<plugin>:<name>` (AC41, R8).
- Блок «Що нового» на головній, дата «оновлено» і сортування «Нещодавно
  оновлені» потребують git-історії, тому вони у v2 (AC64–AC69, AC75).
- У порожньому каталозі посилання `CONTRIBUTING.md` замінено кнопкою
  `Запропонувати плагін` (файлу `CONTRIBUTING.md` у репо немає).
- Макет використовує inline-стилі й Google Fonts. Сайт виносить стилі в CSS-файли,
  а шрифти віддає з власного origin (AC53, A-fonts).
- Accent-кольори `green`/`violet`/`amber` — параметр прев'ю макета. На сайті
  лише `blue`.
- У макеті кнопки `Скинути фільтри` (порожній стан) і `Скинути` (панель
  фільтрів) очищають і запит. На сайті обидві знімають лише фільтри (AC33).
- У макеті порожній запит лишає користувача на екрані пошуку з
  `Огляд каталогу`. На сайті запит без змістовних термів і без фільтрів
  показує головну (AC72).

## Взаємодія модулів
Модулі: **site** — статичні сторінки та клієнтський JS на GitHub Pages;
**index-build** — CI-скрипт, що читає репо і генерує індекс, відрендерені
README, бейджі, фід; **ci** — GitHub Actions workflow для validate, build і
deploy. Бекенду немає. Браузер ходить лише до власного origin, а прев'ю бейджа
вантажиться з `img.shields.io` (AC53).

| Дія | Шлях | Контракт / артефакт | Нове чи є |
|-----|------|------|------|
| Push у `main` / `workflow_dispatch` | `validate.yml`: job `validate` ∥ job `Catalog site · build` (index-build → тести → upload Pages artifact) → job `Catalog site · deploy` (needs обидві) | Pages artifact (R5) | job `validate` є; решта нова |
| PR | `validate.yml`: `validate` ∥ `Catalog site · build`; deploy пропущено | — | нове |
| Локальна розробка | `cd site && npm run dev` → build з робочої копії → сервер `localhost:4321` → перезбирання й live reload при змінах | — | нове |
| Збирання індексу | index-build читає `.claude-plugin/marketplace.json`, `plugins/**`, карту синонімів, стоп-слова, git-історію (v2) | `index.json` (артефакти + метадані build), HTML README кожного плагіна, HTML тіла кожного skill/agent/command, `badges/*.json`, `feed.xml`; вшиває `<owner>/<repo>` і `<marketplace name>` у `getting-started.html` (AC83) | нове |
| Відкрити будь-яку сторінку | site → GET `index.json` (той самий origin) → пошук у браузері | `index.json` | нове |
| Пошук, фільтри, сортування | лише в браузері, без мережі; стан → `history.replaceState` | URL `?q=&type=&category=&tag=&author=&sort=` | нове |
| Палітра `⌘K` | лише в браузері, той самий пошук без фільтрів | — | нове |
| Перемикач теми | site → `localStorage['dd-theme']`; `theme-init.js` у `<head>` застосовує тему до першого рендеру | ключ `dd-theme` = `light` \| `dark` | нове |
| Відкрити артефакт | site → `index.json` → відрендерене тіло артефакту з артефакту сайту | `/artifact.html?plugin=&type=&name=` | нове |
| Copy install / виклик / сніпет | site → Clipboard API | — | нове |
| Запропонувати плагін | site → нова вкладка `github.com/<repo>/issues/new?title=…&body=…` | GitHub new-issue URL | нове |
| Завантажити settings.json (v2) | site → Blob у браузері | файл `settings.json` | нове |
| Прев'ю бейджа (v2) | site → `img.shields.io/endpoint?url=<site>/badges/<plugin>.json` | endpoint JSON (R6) | нове |

Вплив на інших споживачів: у `validate.yml` наявна job `validate` не
змінюється. До workflow додаються дві нові jobs сайту, а workflow отримує
права `pages: write` і `id-token: write` лише на рівні job deploy. Увесь код
сайту лежить у `site/` з власним `package.json`, тож корінь маркетплейсу і
`claude plugin validate .` його не зачіпають. `README.md` не змінюється.
Фікстурний маркетплейс не зачіпає `claude plugin validate .` кореня репо (AC9).

## Acceptance criteria (EARS)

### CI і збирання індексу (ci, index-build)
- **AC1** (event, US7) КОЛИ в `main` з'являється push або запускають
  `workflow_dispatch`, ci повинен (shall) у workflow `validate.yml` виконати
  три окремі jobs: наявну `validate` (harness маркетплейсу, без змін),
  `Catalog site · build` (встановлення залежностей `site/`, build індексу,
  тести, upload Pages artifact) і `Catalog site · deploy` (deploy на GitHub
  Pages). `validate` і `Catalog site · build` виконуються паралельно, і
  кожна має власний статус у вкладці Actions та в checks PR/коміту.
  `[manual]` (мейнтейнер перевіряє запуск у вкладці Actions і оновлений
  сайт)
- **AC2** (unwanted, US7) ЯКЩО `validate` або `Catalog site · build`
  завершилася з помилкою, ТОДІ ci повинен (shall) не виконувати
  `Catalog site · deploy` (вона має `needs` на обидві jobs), і на Pages
  лишається попередня версія сайту. Падіння `Catalog site · build` не
  змінює статусу `validate`, і навпаки. `[manual]` (мейнтейнер пушить у
  тестову гілку з навмисно зламаним плагіном і запускає `workflow_dispatch`
  на ній)
- **AC3** (event, US7) КОЛИ відкривають або оновлюють pull request, ci
  повинен (shall) виконати `validate` і `Catalog site · build`, а
  `Catalog site · deploy` пропустити. `[manual]`
- **AC4** (state, US7) ПОКИ триває deploy попереднього запуску, ci повинен
  (shall) поставити новий deploy у чергу (concurrency-група `pages`,
  `cancel-in-progress: false`), а не скасовувати поточний. Перед deploy job
  перевіряє, що її коміт досі є головою `main`, і пропускає deploy застарілого
  коміту. На сайті в результаті опиняється коміт останнього запуску.
  `[manual]`
- **AC5** (ubiquitous, US1) index-build повинен (shall) створювати по одному
  артефакту на кожен запис `plugins[]` маркетплейсу (plugin), кожен skill,
  agent і command, кожну пару event+matcher hooks (hook) і кожне ім'я
  MCP-сервера (mcp). Враховуються дефолтні розташування, шляхи з `plugin.json`
  та інлайн-компоненти за правилами заміни, додавання й злиття з R2. `[unit]`
- **AC6** (ubiquitous, US1) Кожен артефакт в індексі повинен (shall) мати поля
  `type`, `name`, `plugin` (ім'я батьківського плагіна; у plugin — він сам),
  `description`, `body` (тіло Markdown без frontmatter; для hook і mcp — текст
  команди/URL), `path` (шлях у репо), `tags`, `author`. `author` береться з
  `author.name` запису маркетплейсу, інакше з `plugin.json`; компоненти
  успадковують автора плагіна. `[unit]`
- **AC7** (ubiquitous, US4) index-build повинен (shall) брати `displayName`,
  `description` і `category` плагіна з запису маркетплейсу, коли там вони
  задані, інакше з `plugin.json`. `version` береться з `plugin.json`, а без
  нього — з запису маркетплейсу (R1). `[unit]`
- **AC8** (ubiquitous, US8) index-build повинен (shall) обчислювати теги
  плагіна як об'єднання `tags` запису маркетплейсу та `keywords` з

- **AC9** (ubiquitous, US7) Продакшн-індекс повинен (shall) містити лише
  плагіни з `.claude-plugin/marketplace.json` кореня репо. Жоден плагін

- **AC10** (unwanted, US7) ЯКЩО будь-який JSON-файл, який читає index-build

- **AC14** (ubiquitous, US4) index-build повинен (shall) рендерити README

- **AC15** (ubiquitous, US4) index-build повинен (shall) переписувати відносні

- **AC16** (ubiquitous, US4) index-build повинен (shall) копіювати зображення з

- **AC17** (unwanted, US4) ЯКЩО README містить зображення з абсолютним
  зовнішнім URL, ТОДІ index-build повинен (shall) замінити його посиланням на

- **AC79** (ubiquitous, US12) index-build повинен (shall) зберігати для skill і

- **AC88** (ubiquitous, US4) index-build повинен (shall) зберігати для плагіна

### Пошук (site)
- **AC18** (event, US1) КОЛИ користувач змінює текст у полі пошуку (hero на
  головній або в хедері), UI повинен (shall) через 150 мс після останньої
  зміни показати вигляд результатів і оновити параметр `?q=` (через
  `history.replaceState`). На сторінках, відмінних від `/`, введення в поле
  хедера й `Enter` відкривають `/?q=<q>`. `[e2e]`
- **AC19** (ubiquitous, US1) Пошук повинен (shall) нормалізувати запит і
  поля індексу: lowercase, Unicode NFC, апострофи `’`, `ʼ`, `` ` `` → `'`.
  Далі він прибирає стоп-слова з підтримуваного списку без урахування
  регістру. Мінімальний англійський список: `i, need, want, looking, find,
  a, an, the, for, to, me, my, some, something, that, which, with, help,
  please, can, you, of, in, on, and, or, is, are, how, do`. Мінімальний
  український: `мені, треба, потрібен, потрібна, потрібно, потрібні,
  хочу, шукаю, знайти, знайди, для, щоб, який, яка, яке, які, якийсь, щось,
  з, із, зі, в, у, на, і, й, та, або, чи, як, що, це, є, будь, ласка,
  допоможи, допомога`. Для фікстур запит `I need help with code review` і
  запит `Мені треба щось для code review` дають той самий упорядкований
  список, що й `code review`. `[unit]`
- **AC20** (ubiquitous, US1) Пошук повинен (shall) розпізнавати в запиті
  слова-типи, застосовувати їх як фільтр типу і вилучати з пошукових термів.
  Англійські: `plugin(s)`, `skill(s)`, `agent(s)`, `command(s)`, `hook(s)`,
  `mcp`. Українські (усі відмінкові форми однини й множини): `плагін`,
  `скіл`/`скілл`, `агент`, `команда`, `хук`. Запити
  `I need a skill for code review` і `мені треба скіл для code review` дають
  ті самі результати, що й `code review` з фільтром `type=skill`. `[unit]`
- **AC21** (event, US1) КОЛИ після вилучення стоп-слів і слів-типів не лишилося
  жодного терма, UI повинен (shall) показати всі артефакти розпізнаного типу,
  відсортовані за назвою. Якщо типу не розпізнано і фільтрів немає, діє AC72.
  `[unit]` `[e2e]`
- **AC22** (ubiquitous, US1) Пошук повинен (shall) зважувати збіги за полями:
  `name` ×3, `tags` ×2, `description` ×2, `body` ×1. Для фікстур артефакт із
  термом лише в `name` стоїть вище за артефакт із тим самим термом лише в
  `body`. `[unit]`
- **AC23** (ubiquitous, US1) Пошук повинен (shall) зіставляти кожен терм
  довжиною ≥ 2 символи як префікс (`rev` знаходить `review`), а терми
  довжиною ≥ 5 символів — також із відстанню редагування ≤ 1 (`reveiw`
  знаходить `review`). `[unit]`
- **AC24** (ubiquitous, US8) Пошук повинен (shall) розширювати кожен терм, що є
  ключем карти синонімів, усіма його синонімами з карти. Карта приймає
  українські ключі з англійськими синонімами: для фікстур із записом
  `"рефакторинг": ["refactor", "refactoring"]` запит `рефакторинг` знаходить
  артефакт, у якому є лише `refactor`. `[unit]`
- **AC25** (event, US8) КОЛИ під час запиту спрацювало розширення синонімами,
  UI повинен (shall) показати під полем рядок
  `Також шукали: <term> → <syn1>, <syn2>`, по одному фрагменту на кожен
  розширений терм, розділені ` · `. `[e2e]`
- **AC26** (ubiquitous, US1) Картка результату повинна (shall) показувати
  мітку типу кольором `--kind-<type>` і текстом (`plugin`, `skill`, `agent`,
  `command`, `hook`, `MCP`), версію `v<version>` батьківського плагіна,
  назву, сніпет ≤ 160 символів з `…` при обрізанні та з виділеними збіглими
  термами (опис, а якщо збіг лише в `body` — фрагмент `body` навколо

  `[e2e]`
- **AC27** (ubiquitous, US1) UI повинен (shall) вставляти назви, описи й
  сніпети як текст. Опис фікстури `<img src=x onerror=alert(1)>`
  відображається буквально, і жоден скрипт не виконується. `[unit]` `[e2e]`
- **AC28** (event, US1) КОЛИ запит дає більше ніж 50 результатів, UI повинен
  (shall) показати перші 50 у поточному порядку сортування і кнопку

- **AC29** (ubiquitous, US1) UI повинен (shall) показувати над картками
  заголовок `Результати: “<q>”` (або `Огляд каталогу` без запиту) і рядок з
  повною кількістю збігів за правилами множини `Intl.PluralRules('uk')`:

- **AC30** (ubiquitous, US5) Картка плагіна і сторінка плагіна повинні (shall)

  `Запускає MCP-сервер` (≥ 1 MCP), `Запускає LSP-сервер` (≥ 1 LSP),
  `Запускає monitors` (≥ 1 monitor), `Запускає бінарники` (≥ 1 файл у

- **AC31** (state, US1) ПОКИ запит порожній, але активний хоча б один
  фільтр, UI повинен (shall) показувати під заголовком `Огляд каталогу` всі
  артефакти, що проходять фільтри, відсортовані за показуваною назвою без

- **AC32** (unwanted, US1) ЯКЩО запит та/або фільтри дають 0 результатів,

  `Спробуйте скинути фільтри або змінити запит.` і кнопку
  `Запропонувати плагін`. Кнопка `Скинути фільтри` з'являється, лише коли

- **AC33** (event, US2) КОЛИ користувач натискає `Скинути фільтри` (у
  порожньому стані) або `Скинути` (у панелі фільтрів), UI повинен (shall)

- **AC34** (unwanted, US1) ЯКЩО в індексі 0 плагінів, ТОДІ головна повинна

### Фільтри та URL (site)
- **AC36** (ubiquitous, US2) UI повинен (shall) пропонувати в панелі
  `Фільтри` групи `Тип` (шість типів із кількістю), `Категорія` (усі
  категорії з індексу), `Keywords` (усі теги з індексу, за алфавітом) і
  `Автор` (усі автори з кількістю; артефакти без автора — у групі
  `Невідомий автор`). Значення всередині групи об'єднуються через АБО, групи
  між собою — через І. `[unit]` `[e2e]`
- **AC37** (event, US2) КОЛИ користувач змінює запит, фільтр або сортування,
  UI повинен (shall) записати стан в URL як
  `?q=<q>&type=<t1,t2>&category=<c>&tag=<g1,g2>&author=<a>&sort=<s>` і
  пропустити порожні параметри та `sort` зі значенням за замовчуванням.
  `[e2e]`
- **AC38** (event, US2) КОЛИ користувач відкриває URL з параметрами `q`,
  `type`, `category`, `tag`, `author`, `sort`, UI повинен (shall) відновити
  поле пошуку, фільтри, сортування й результати, ідентичні тим, що були в
  момент копіювання URL. `[e2e]`
- **AC39** (unwanted, US2) ЯКЩО параметр URL містить невідоме значення типу,
  категорії, тегу, автора чи сортування, ТОДІ UI повинен (shall)
  проігнорувати це значення й застосувати решту. `[unit]`
- **AC74** — номер не використовується (зарезервовано під час редагування).
- **AC75** (event, US2) КОЛИ користувач вибирає значення в списку
  `Сортувати`, UI повинен (shall) упорядкувати результати: `За релевантністю`
  (за замовчуванням; без запиту — за назвою), `За назвою` (`sort=name`, без
  урахування регістру, `localeCompare` з локаллю `uk`). У v2 додається
  `Нещодавно оновлені` (`sort=updated`, за датою останнього запису історії
  плагіна, AC64). `[unit]` `[e2e]`

## Edge cases
- **EC1** Запит лише зі стоп-слів (`I need a`, `мені треба щось`) → головна,
  запит лишається в полі (AC19, AC21, AC72).
- **EC2** Запит лише зі слова-типу (`skills`, `скіли`, `агентів`) → усі артефакти цього типу за
  назвою (AC20, AC21).
- **EC3** Запит > 200 символів або зі спецсимволами regex і HTML → обрізання
  до 200, без помилки, як звичайний текст (AC35, AC27).
- **EC4** HTML або скрипт в описі, назві чи тілі SKILL.md → показується як
  текст (AC27).
- **EC5** Однакове ім'я skill у двох плагінах → дві картки, які розрізняє
  батьківський плагін (AC26).
- **EC6** Довгий опис → сніпет ≤ 160 символів з `…` (AC26).
- **EC7** > 50 результатів → `Показати ще 50` (AC28).
- **EC8** 0 плагінів у маркетплейсі → `Каталог порожній` (AC34); у
  «Як підключити» крок 2 з плейсхолдером `<plugin>` (AC83).
- **EC9** Плагін із `source` поза репо (github, git-subdir, npm тощо) →
  індексуються лише поля запису (AC47).
- **EC10** Невалідний JSON, frontmatter без `name`/`description`, зламана
  карта синонімів → build падає, deploy не відбувається (AC10, AC2).
- **EC11** README з `<script>`, `onerror`, `javascript:`, зовнішнім зображенням
  → санітизовано, зовнішнє зображення стає посиланням `зображення: <alt>`
  (AC14, AC17).
- **EC12** Літеральний секрет в `env` або `headers` → публікуються лише імена
  (AC13).
- **EC13** Невідомий плагін у `?name=` → `Плагін "<name>" не знайдено` (AC48);
  невідомий артефакт → `Артефакт не знайдено` (AC81).
- **EC14** Невідомі значення в `?type=` / `?tag=` / `?bundle=` → ігноруються
  (AC39, AC61).
- **EC15** Clipboard недоступний (http, відмова, старий браузер) → поле для
  ручного копіювання (AC42).
- **EC16** Shallow checkout в CI (v2) → build падає з поясненням (AC65).
- **EC17** Індекс недоступний або битий (404, мережа, частково записаний
  артефакт) → `Не вдалося завантажити індекс плагінів.` + `Спробувати ще`
  (AC50).
- **EC18** Два push-и поспіль → deploy-и в черзі, на сайті останній коміт (AC4).
- **EC19** Hooks одночасно в `hooks/hooks.json` і в `plugin.json` → обидва
  джерела злито, кожна пара event+matcher — окремий артефакт (AC5).
- **EC20** Індекс застарів відносно репо (зміна без rebuild) → очікувано;
  свіжість видно у футері (AC52).
- **EC21** Український запит без синоніма в карті (`тестування`, коли вміст
  лише англійською) → 0 результатів, порожній стан із `Запропонувати
  плагін` (AC32). Покриття залежить від карти синонімів (AC24).
- **EC22** Різні апострофи (`рев'ю`, `ревʼю`, `рев’ю`) → однаковий результат
  (AC19).
- **EC23** `localStorage` заблоковано (приватний режим, політика браузера) →
  тема перемикається лише в межах сторінки, без помилки (AC77).
- **EC24** Збережена тема відрізняється від системної → застосовується
  збережена, без спалаху (AC76).
- **EC25** `⌘K` поки відкрита палітра або фокус у полі пошуку → палітра
  перемикається, браузерний шорткат не спрацьовує (AC84).
- **EC26** Agent без `tools` / skill без `allowed-tools` → `Успадковує всі
  інструменти сесії` / `Додаткових дозволів не надає` (AC80).
- **EC27** Довгі українські слова й назви на ширині 320 px → перенос без
  горизонтального скролу (NFR6).

## Non-functional requirements
- **NFR1** Латентність пошуку: ≤ 50 мс p95 на один запит (токенізація,
  синоніми, пошук, сортування; без рендеру) на синтетичному індексі з 2 000
  артефактів — перевірка: unit-бенчмарк на 200 запитах у Node 22 на CI-раннері
  `ubuntu-latest`.
- **NFR2** Розмір індексу: ≤ 1 MB gzip на синтетичному маркетплейсі з 200
  плагінів / 2 000 артефактів — перевірка: it-тест збирає синтетичний індекс і
  міряє gzip-розмір.
- **NFR3** JS-бандл: сумарно ≤ 100 KB gzip для всіх скриптів сторінки,
  включно з бібліотекою пошуку — перевірка: it-тест міряє артефакт.
- **NFR12** Шрифти: IBM Plex Sans (400/500/600/700) і IBM Plex Mono
  (400/500/600) у WOFF2 з підмножинами latin + cyrillic, сумарно ≤ 400 KB,
  `font-display: swap` — перевірка: it-тест міряє файли шрифтів в артефакті.
- **NFR4** Завантаження: Lighthouse (mobile) Performance ≥ 90 і LCP ≤ 2.5 с на
  головній, у результатах і на сторінці плагіна — перевірка: `[manual]` мейнтейнер запускає
  Lighthouse на опублікованому сайті після першого deploy.
- **NFR5** Доступність WCAG 2.2 AA: 0 порушень рівня serious/critical в axe на
  головній, у результатах, на сторінках плагіна й артефакту, «Як підключити»,
  з відкритою палітрою `⌘K`, на «Набір для команди» і Що нового — у світлій і темній
  темах.
  Контраст тексту ≥ 4.5:1, target ≥ 24×24 px, видимий фокус, усі контроли
  досяжні з клавіатури, у фільтрів є label — перевірка: axe у e2e.
- **NFR6** Адаптивність: на ширині 320 px немає горизонтального скролу, і всі
  контроли доступні — перевірка: e2e з viewport 320×640.
- **NFR7** Браузери: дві останні стабільні версії Chrome, Firefox, Safari,
  Edge — перевірка: e2e у Chromium, Firefox і WebKit.
- **NFR8** Час build: крок index-build ≤ 60 с на синтетичному маркетплейсі з
  200 плагінів — перевірка: it-тест з таймаутом.
- **NFR9** Свіжість: сайт відображає коміт з `main` ≤ 10 хв після push за
  успішного CI — перевірка: `[manual]` мейнтейнер порівнює SHA у футері з
  комітом.
- **NFR10** Ланцюг постачання: залежності зафіксовано lock-файлом, `npm audit`
  дає 0 high/critical на момент deploy — перевірка: крок CI перед build.
- **NFR11** Без JS-фреймворку і SSG: в артефакті сайту лише статичні HTML, CSS
  і JS — перевірка: рев'ю залежностей у PR.

## Untrusted inputs
- README → UI (HTML) → рендер у CI, allowlist-санітайзер, переписування

- Назви, описи, тіла skill/agent/command, команди hooks/MCP → UI → вставка

- Тіла skill/agent/command → UI (HTML) → ті самі рендер, санітайзер і CSP,

## Assumptions
- **Рівні верифікації в цьому репо** (тестового набору ще немає):
  `[unit]` — Node-тести логіки index-build (на фікстурному маркетплейсі) і
  пошуку (токенізація, стоп-слова, синоніми, ранжування, URL-стан);
  `[it]` — повне збирання артефакту сайту з фікстур і перевірки
  згенерованих файлів (склад індексу, розміри, CSP, відсутність секретів);
  `[e2e]` — браузерний тест (Chromium/Firefox/WebKit) проти зібраного з
  фікстур сайту, відданого локальним статичним сервером;
  `[manual]` — перевірки GitHub Actions і Pages, які виконує мейнтейнер.
- **Фікстурний маркетплейс** лежить поза `.claude-plugin/marketplace.json`
  кореня і поза `plugins/`, тож `claude plugin validate .` його не бачить.
  Він містить 4–5 плагінів, що разом покривають: усі шість типів, skill за
  шляхом із `plugin.json`, inline-hook, stdio- і http-MCP з `env`/`headers`
  та значенням-маркером, LSP, monitor, файл у `bin/`, `tags` + `keywords`,
  README з `<script>`, `onerror`, зовнішнім і відносним зображенням, плагін
  без README, плагін з `source` типу `github`, плагін з `dependencies`
  (рядок на плагін фікстур, об'єкт із `version`, залежність з іншого
  маркетплейсу), агент у підтеці `agents/<dir>/`. Окремий фікстурний набір із
  битим JSON і frontmatter використовується лише для AC10.
- **URL сайту**: `https://aptrnk1.github.io/dev-digest-ai-marketplace/`.
  Сторінки: `/`, `/plugin.html?name=<name>`,
  `/artifact.html?plugin=<p>&type=<t>&name=<n>`, `/getting-started.html`,
  `/bundle.html`, `/whats-new.html`; файли `index.json`, `feed.xml`,
  `badges/*.json`. Це
  публічні адреси, тому їх зафіксовано як контракт.
- `<owner>/<repo>` береться з оточення CI, `<marketplace name>` — з поля
  `name` у `marketplace.json`. Нічого не захардкоджено.
- **Ручні кроки один раз**: у налаштуваннях репо Pages має джерело
  «GitHub Actions»; репо публічне.
- Увесь проєкт сайту лежить у `site/`: `package.json`, `src/` (шаблони, CSS,
  JS, `i18n/uk.json`), `scripts/` (build, dev), `data/` (синоніми,
  стоп-слова), `test/` (unit, it, e2e, фікстури). Збірка йде в `site/dist/`,
  яку не комітять.
- Посилання на сайті відносні, бо Pages віддає його з підшляху
  `/dev-digest-ai-marketplace/`. В артефакті є `.nojekyll`.
- **Масштаб для NFR**: до 200 плагінів і 2 000 артефактів. Зараз — 5 плагінів
  і близько 22 артефактів.
- **A-fonts.** Шрифти IBM Plex (SIL OFL 1.1) лежать в артефакті сайту, тож
  CSP `default-src 'self'` їх дозволяє. Google Fonts не використовуються,
  ліцензія шрифту йде поруч із файлами.
- **A-styles.** CSP `style-src 'self'` блокує inline-атрибути `style`. Тому
  inline-стилі макета переносяться в CSS-класи, а динамічні значення (колір
  типу) задаються через класи `kind-<type>`.
- **A-lang.** Вміст плагінів (SKILL.md, описи) англійською. Українські
  запити знаходять його через назви, теги, технічні терміни латиницею і
  українсько-англійську карту синонімів. Мейнтейнер наповнює карту
  українськими ключами для кожного тегу й категорії з індексу. Перевірка
  повноти — `[manual]`, рев'ю PR.
- **A-theme.** Ключ `localStorage` `dd-theme` спільний для всіх сторінок
  (той самий origin). `theme-init.js` ставить `data-theme` на `<html>`.
- **Семантика фільтрів**: АБО всередині групи, І між групами (AC36).
- Стоп-слова й карта синонімів — файли в репо, які веде мейнтейнер; зміни
  набувають чинності після наступного build.
- **R1** (https://code.claude.com/docs/en/plugins/marketplace-reference.md,
  2026-10-25): у записі маркетплейсу є `category`, `tags` («Free-form tags for
  search»), `displayName`. Display-поля запису мають пріоритет над
  `plugin.json`, `version` з `plugin.json` має пріоритет над записом.
- **R2** (https://code.claude.com/docs/en/plugins-reference, 2026-10-25):
  дефолтні розташування компонентів — `skills/<n>/SKILL.md`, `commands/`,
  `agents/`, `hooks/hooks.json` (з обгорткою `"hooks"`), `.mcp.json`,
  `.lsp.json`, `monitors/monitors.json`, `bin/`. `plugin.json` може задавати
  шляхи й інлайн-конфіги: `commands`/`agents` замінюють дефолт, `skills`
  додаються, `hooks`/`mcpServers`/`lspServers` зливаються. `keywords` —
  «Discovery tags». Компоненти називаються `<plugin>:<name>`.
- **R3** (https://code.claude.com/docs/en/plugins/org.md, 2026-10-25): у
  `.claude/settings.json` репо `extraKnownMarketplaces` (ключ — `name`
  маркетплейсу, `source: {source: "github", repo}`) і `enabledPlugins`
  (`"<plugin>@<marketplace>": true`). `extraKnownMarketplaces` застосовується
  після того, як людина довірила теку. Плагіни з relative-path source
  встановлюються з копії маркетплейсу.
- **R4** (https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api,
  2026-10-25): без автентифікації — 60 запитів/год; `GITHUB_TOKEN` в Actions —
  1 000 запитів/год на репо.
- **R5** (https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages,
  2026-10-25): деплой через `configure-pages` / `upload-pages-artifact` /
  `deploy-pages`, права `pages: write` + `id-token: write`, environment
  `github-pages`, артефакт < 10 GB без symlink-ів.
- **R6** (https://shields.io/badges/endpoint-badge, 2026-10-25): endpoint JSON
  `{schemaVersion: 1, label, message, color?}`, URL
  `https://img.shields.io/endpoint?url=…`.
- **R7** (https://htmhell.dev/adventcalendar/2023/7/, 2026-10-25): GitHub
  Pages не дає задавати HTTP-заголовки; CSP задається через
  `<meta http-equiv>`. Що meta-CSP не підтримує `frame-ancestors`, узято із
  загальних знань — clickjacking-захисту через CSP немає. Ризик прийнято: на
  сайті немає дій зі станом.
- **R8** (https://code.claude.com/docs/en/plugins/manifest-reference.md,
  https://code.claude.com/docs/en/plugins/dependencies.md,
  https://code.claude.com/docs/en/sub-agents.md, 2026-10-25): `dependencies`
  у `plugin.json` — масив рядків `"name"` / `"name@marketplace"` або
  об'єктів `{name, marketplace, version}` із semver-діапазоном. Поля для
  мінімальної версії Claude Code в маніфесті немає. Агент плагіна
  викликається через `@agent-<plugin>:<name>`; агент із підтеки
  `agents/review/security.md` має ідентифікатор `<plugin>:review:security`.

## Open questions
- **OQ1** Чи додавати `"autoUpdate": true` у запис `extraKnownMarketplaces`
  сніпета Bundle (AC59)? Варіанти: (a) не додавати — поточна поведінка спеки,
  бо R3 підтверджує поле лише для managed settings; (b) додати, якщо
  дослідження підтвердить, що його читають і в project settings. Вирішує
  власник репо (aptrnk1). Non-blocking.

  Мітка має вже існувати в репо. Варіанти: (a) без мітки — поточна поведінка
  AC51; (b) створити мітку й додати параметр. Вирішує власник репо.
  Non-blocking.
- **OQ3** — закрито 2026-10-25: `Залежності` беруться з `dependencies` у
  `plugin.json` (AC88, AC89). `compatibility` не показується, бо маніфест
  такого поля не має (R8).
